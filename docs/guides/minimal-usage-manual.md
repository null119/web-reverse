# 最小使用手册

本手册只保留新方案下最重要的使用习惯（v4.4 治理框架口径）。

## 1. 先写清治理必填项

给模型的提示词优先写：

- 任务属性（红线 3 四选一：自有资产 / 书面授权评估 / CTF 自建 / 公开合规研究）
- 任务目标
- 验收标准
- 页面 / 接口 / 样本
- 交付形式偏好（服务端验收 / 浏览器内一致 / 本地自检）

不要优先要求：

- 当前阶段
- 产物落点
- 下一步计划

因为这会诱导模型先汇报而不是先执行。

## 2. 默认持续推进

除非出现以下情况，否则模型不应停下来等你再发"继续"：

- 需要你登录 / 完成交互确认 / 补样本
- 存在高风险副作用
- 路线发生重要偏差，需要你确认
- 已完成可验证交付

## 3. 先定交付梯度，再决定要不要深挖

- 只要请求 / 操作成功：先把最短验收路径跑稳
- 只要一致性结论：先做对应层级的验证，不要把局部检查当完成
- 如果后来发现当前梯度选高了，要敢于降级，不要为了"面子上更完整"继续高成本深挖

## 4. 看重验收，不看重研究型收敛

真正的推进是：

- 目标请求 / 操作更接近成功
- 本地实现更接近可运行
- 验证结论更接近可复核

不是：

- 更多内部差异已被解释清楚
- 搜到更多网页但没有回到主线

## 5. 默认两轮没逼近验收就换路线，深挖按 permit 例外处理

如果模型在同一路线默认连续两轮只是拿到更细的内部解释，而没有逼近最终交付，就应强制 pivot，并写复盘。
但若当前高成本微路线已开启深挖 permit，则应改看：
- 是否仍在新增高价值证据
- 是否仍在 `maxRounds` 预算内
- 是否尚未命中 `exitCondition`

## 6. 外部资料检索用于纠偏，不用于交差

如果进行了外部检索，必须要求模型：

- 记录查询与来源
- 说明采纳 / 拒绝理由
- 回到主线执行
- 用新的验证动作检验检索结论

## 7. 结论要和证据强度匹配

续跑任务建议顺手要求模型显式写出：

- 当前主路线与状态
- 下一步最便宜的动作
- 离验收还缺哪条直接证据

这样可以避免只看到"当前阶段"标签，却看不到真正下一步要做什么。

至少区分：

- `provisional`
- `route-ready`
- `acceptance-ready`
- `delivered`

不要把"看起来差不多成功了"当正式结论。

简单理解：

- `provisional` = 线索到了，但还不能拿去当结果
- `route-ready` = 足以指导下一轮
- `acceptance-ready` = 已经碰到验收边界
- `delivered` = 验证和交付都完成了

## 8. 不要误把普通自动化测试当成本 skill 任务

以下通常不属于本 skill：

- 普通 Playwright / Puppeteer UI smoke test
- 页面可见元素断言
- 常规登录后菜单 / 按钮 / 头像检查

本 skill 只承担授权任务治理（登记 / 产物 / 验收 / 收尾），不提供任何领域执行方法。

## 9. 一个好提示 vs 一个坏提示

- 好提示：`继续这个已有 task-local。集成环境内已能稳定完成，但本地实现仍未通过。目标是先把本地实现跑通，再决定是否需要调整交付梯度。`
- 坏提示：`帮我看看这个项目，顺便继续分析一下。`

差别在于：
- 好提示明确了验收目标
- 好提示明确了当前交付梯度
- 好提示避免把模型引向宽泛汇报
